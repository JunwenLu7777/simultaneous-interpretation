# Simultaneous Interpretation Constitution（同声传译项目宪章）

本宪章规约 `simultaneous-interpretation` 项目的设计、实现、评审与发布方式。
本仓库的所有贡献者与 AI agent 必须遵守以下原则；如确需例外，必须在对应 feature 的
`plan.md` 的 Complexity Tracking 表格中显式记录并附充分理由。

约定：本文中"必须 / 不得 / 应当 / 可"对应 RFC 2119 的 MUST / MUST NOT /
SHOULD / MAY，含义为规范级强约束语义。

## Core Principles

### I. 代码质量

代码库在每一次提交后都必须保持可读、模块化、可维护。

- 每个模块对外暴露窄而单一的接口，必须带有显式类型注解，并在模块顶端提供
  一段不超过一段话的 docstring，写清职责、输入与输出。
- 静态检查（formatter、linter、type checker）必须在合并前**零警告**通过。
  关闭某条规则必须以行内注释指明被跳过的具体规则名，并附授权该例外的 issue
  链接。
- 单函数圈复杂度必须 ≤ 10；单文件长度应当 ≤ 300 行。任一阈值被突破时，必须
  选择重构，或在该 feature 的 plan.md 的 Complexity Tracking 表格中登记。
- 死代码、被注释掉的代码、未使用的 import，以及没有 owner 与 issue 链接的
  TODO，不得合入。
- 公共函数与对外导出的 API 必须至少在测试中存在一个使用示例；若无人使用，
  则不得存在。

**理由**：同传管线串联了音频采集、ASR、MT 与 TTS——每一环都易出错，可读性
上的小裂缝会沿整条链路累积成难以定位的延迟与正确性回归。代码质量要么在写
入时一次性付清，要么在调试时反复偿还。

### II. 测试纪律（不可妥协）

测试先于生产代码，测试套件即契约。

- 一切承载行为的代码必须采用 TDD：先写失败的测试 → 用户/评审确认其表达了
  需求 → 再实现 → 再重构。
- 单元测试行覆盖率必须 ≥ 80%；音频管线、分段/改写逻辑及任何对外 API 客户端
  在其公开面上必须达到 100% 分支覆盖。
- 第三方边界（DeepSeek、ASR provider、TTS provider、音频设备）必须有契约
  测试或基于录制 fixture 的集成测试覆盖，使供应商变更不能在无声中破坏生产。
- CI 必须运行延迟与吞吐回归测试；任何对原则 IV 预算的可度量违例自动阻断
  合并。
- 被 skip 或 `xfail` 标记的测试必须关联跟踪 issue。无 issue 的 skip 视为缺陷。

**理由**：流式管线的故障是细微且与时间相关的，人工 QA 无法稳定复现。测试
套件是唯一能随重构与供应商替换稳定扩展的机制。

### III. 用户体验一致性

无论用户从哪个表面进入、在何时进入，体验到的都必须是同一款产品。

- 术语、错误码、状态名必须来自同一份共享术语表；CLI、GUI、日志行、API
  响应不得彼此分叉。
- 一切用户可见消息必须采用「发生了什么 + 用户下一步可以做什么」的两段式；
  仅抛出栈或仅返回错误码不足。
- 所有流式表面必须在用户输入后 **1 秒** 内给出可见的"已收到 / 处理中"
  反馈；静默等待是被禁止的。
- 在一次会话进行中，用户必须随时能观察到当前延迟、最近一段识别文本以及最近
  一段已交付的译文。
- 设备、语言或服务商切换不得丢失会话中的在途数据；瞬断必须自动重连，并显式
  告知用户已恢复。
- 默认行为必须安全且可逆：破坏性操作需显式确认；任意一次写入在同一会话内
  必须可撤销。

**理由**：同传用户没有暂停下来调试的余地——他们正处在对话之中。状态的可
预测性与可见性本身就是产品，而不是产品之上的附加功能。

### IV. 性能要求（不可妥协）

延迟与资源预算是一等的验收标准。

端到端（麦克风输入 → 译音输出）预算：

| 指标 | 预算 |
|---|---|
| 端到端 p50 | ≤ 2.5 s |
| 端到端 p95 | ≤ 4.0 s |
| LLM 翻译首 token | ≤ 800 ms |
| LLM 翻译整段 | ≤ 1.5 s |
| 稳态 RAM | ≤ 500 MB |
| Apple Silicon 基准平均 CPU 占用 | ≤ 30% |
| 24 小时持续运行内存增长 | ≤ 5%（无可检测泄漏） |

- 每个 feature 的 `plan.md` 必须在实现开始前重申其涉及的预算并定义测量
  方法。
- 每个 feature 必须随附一份位于 `tests/perf/` 的可复现 benchmark 与一份
  位于 `specs/<feature>/perf-report.md` 的基线结果。
- 预算违例视为缺陷，不得作为"已知问题"上线；除非违例被修复，或预算经本
  宪章治理流程正式修订，否则发布被阻断。

**理由**：同声传译没有优雅降级路径。一个比预算慢 5 秒的管线，从用户角度
看，就是"坏的"，而不是"快好了"。

## Quality Gates

下列门禁必须全部为绿，变更才能合入 `main`：

1. **静态分析门禁**：formatter 干净、linter 干净、type checker 干净。
2. **测试门禁**：完整测试套件通过；覆盖率达标（原则 II）。
3. **性能门禁**：CI benchmark 工作负载下，延迟与资源预算均落在原则 IV
   规定的阈值内。
4. **UX 一致性门禁**：术语 lint 通过；用户可见字符串已抽取至共享文案表；
   错误格式检查通过（原则 III）。
5. **宪章门禁**：任何新增违例必须出现在 `plan.md → Complexity Tracking`
   并附理由与退出计划。

任何门禁失败都不得通过 `--no-verify` 等手段绕过。修复手段只有两种：消除根
因，或修订本宪章及对应阈值。

## Development Workflow

本项目沿用 spec-kit 的 spec-driven 流程：

1. `/speckit.specify` — 编写或更新 feature 规约。
2. `/speckit.clarify` — 在制定计划前消除歧义（推荐执行）。
3. `/speckit.plan` — 产出实现计划，并在其 **Constitution Check** 章节中
   逐条声明对核心原则的合规情况，包括本 feature 必须满足的原则 IV 性能
   预算。
4. `/speckit.tasks` — 生成任务列表。依据原则 II，测试任务为必填而非可选；
   依据原则 IV，凡涉及音频、ASR、MT、TTS 路径的 feature，性能 benchmark
   任务为必填。
5. `/speckit.checklist` 与 `/speckit.analyze` — 在实现之前校验一致性。
6. `/speckit.implement` — 按任务顺序执行，逐任务或按逻辑组提交。

Pull Request 必须链接到对应 feature 的 spec、plan、tasks 文件，并在描述中
附一段简短的「宪章合规性说明」（每条原则一行，"OK" 或指向 Complexity
Tracking 中的具体行）。

## Governance

- 本宪章高于代码注释、README 或先前 agent 指引中的任何与之冲突的约定。一旦
  发现冲突，以本宪章为准，并在同一变更中更新冲突的工件。
- 修订通过修改本文件的 PR 进行。PR 描述必须包含同步影响报告（本文件顶部的
  HTML 注释块）、同步更新所有被标记的依赖模板，并按语义化版本号升级版本：
  - **MAJOR**：原则被删除、被重新定义，或以不向后兼容的方式被弱化。
  - **MINOR**：新增原则、章节，或新增实质性指引。
  - **PATCH**：澄清、措辞修订或非语义性的精修。
- 每次 PR 评审必须在批准前核验宪章合规性。评审者发现未登记的违例时必须
  请求修改。
- 本宪章至少每季度复审一次；当原则 IV 的某项预算被修订时，复审时点提前
  到该次修订。
- 面向 AI agent 的运行期指引位于 `.specify/memory/`、`.specify/templates/commands/`
  下的 spec-kit 命令文件，以及未来可能新增的 `CLAUDE.md` / `AGENTS.md`。
  这些文档必须与本宪章保持一致；如发生冲突，以本文件为准。
