# 功能规约：Teams 实时双向语音同传桥（macOS）

**功能分支**：`001-teams-voice-interpreter`
**创建日期**：2026-05-05
**状态**：草稿（Draft）
**输入**：用户描述："设计一套适用于 macOS、与 Microsoft Teams 桌面端深度集成的低成本双向实时语音同传方案；通过 Mac 内置麦克风与扬声器，借助虚拟音频驱动（如 BlackHole / Loopback）完成上下行音频路由，使用流式 STT、流式机器翻译（DeepSeek API）、流式 TTS 实现中英互译；首段译音延迟 ≤ 800 ms；不得开发原生 Mac App、不得开发 Teams 插件，优先使用脚本（Python / Go）或 Web 技术。"

## 澄清记录

### 2026-05-05 会话

- Q: 远端会议方的「被翻译 / 被云端处理」是否需要显式知情同意，本规约如何处置该合规义务？ → A: **v1 完全规避**。规约显式声明本系统**不**适用于医疗、律师、政府、金融、HR 等监管严格场景，仅面向普通商务交流的个人自用；任何监管严格场景与团队/企业级部署**延至 v2**作为独立 feature 重新规约。详见「假设」段「v1 适用场景边界（合规免责）」与「成功标准」段 SC-011。
- Q: 一台 Mac 是否支持同时运行多个并行的同传会话（多个 Teams 实例 / 多账号）？ → A: **v1 仅单会话单 Teams**。再次启动时**必须**拒绝并给出「请先停止当前会话」提示；多会话并行场景延至 v2 处理。详见 FR-026 与「假设」段「v1 单实例约束」。
- Q: 专有名词、产品名、人名、缩写如何在翻译中保持一致？是否需要术语表注入机制？ → A: **静态术语表**。用户在 `~/.config/teams-voice-interpreter/glossary.toml` 中维护一份中英对照术语表，启动时一次性注入 DeepSeek system prompt；**v1 不支持运行时热更新**，自适应/会话内学习延至 v2。详见 FR-012 与「关键实体」段 GlossaryEntry。
- Q: 会话结束后是否提供对话记录导出？格式与触发方式如何？ → A: **导出双语对照 Markdown**。用户在 Web 控制台点「导出」按钮即可下载 `teams-session-<时间戳>.md`，含时间戳 + 双向 + 中英对照，**不**含延迟元数据 / 置信度 / 原始音频；JSON / SRT / 自动弹窗等延至 v2。详见 FR-024 / FR-027。
- Q: 进程级崩溃（Whisper.cpp 子进程或 Python 主进程）的恢复策略？ → A: **进程内 supervisor + 匿名崩溃报告**。CLI 主进程监控核心子进程，子进程崩溃 ≤ 5 秒自动 respawn；主进程崩溃由用户手动 restart；崩溃前写匿名报告到 `~/.cache/teams-voice-interpreter/`（仅 stack trace + 服务状态，**不**含音频/对话/凭证）。**不**引入 launchd / supervisord / pm2 等系统级守护。详见 FR-028 / FR-029 与 US4 验收场景 4。

## 用户场景与测试 *（必需）*

> 用户故事按重要性排序，每条故事必须**独立可测试**——即仅交付其中一条也能构成可上线的最小可用产品（MVP），并向用户独立交付价值。

### 用户故事 1 — 上行同传：用户说中文，对方听到英文（优先级：P1）

一位以中文为母语的 Mac 用户加入 Microsoft Teams 桌面端的英语商务会议。会议进行中，他用中文自然发言；远端的英语同事在不做任何额外配置、仅依赖 Teams 内置语音通道的前提下，**就听到流式的英文译音**——而不是字幕、也不是等他说完一整段后才听到一段录播。

**为什么优先**：「让对方听懂我」是双向同传中两个独立可上线切片里更主导沟通节奏的一个：能否被听懂直接决定会议能否推进。仅交付这一条就构成可用 MVP（用户可以用中文参加英语会议，听不懂的部分用文字补足）。

**独立测试**：用户在 Teams 测试通话中将麦克风切换为本系统提供的虚拟设备，开启上行同传，朗读一段标准商务中文台词；远端 Teams 客户端录音回放可听到流式英文译音；首段译音延迟可由外部时钟测得。

**验收场景**：

1. **假设** 用户已完成首次配置（虚拟音频驱动安装、Teams 麦克风指向虚拟设备、API 凭证已提供），**当** 用户点击「开始同传」并对内置麦克风说出一段中文（≥ 5 个汉字、连续音节），**那么** 远端 Teams 客户端在用户开口后 ≤ 1200 ms 内开始听到对应英文译音（2026-05-07 宪章修订自 800 ms；持续优化软目标 ≤ 1000 ms），且无需等到整句结束。
2. **假设** 上行同传已运行，**当** 用户连续讲话 60 秒（混合长短句），**那么** 远端听到的英文音频应连贯、不间断（允许自然断句间停顿 ≤ 0.6 秒），且与原中文意思一致（盲测可懂度评分 ≥ 4/5）。
3. **假设** 用户中途停止说话 ≥ 5 秒，**当** 静音持续，**那么** 系统不向远端发送任何虚假/幻听的合成音频，并自动闭合上一段翻译片段。

### 用户故事 2 — 下行同传：远端说英文，用户听到中文（优先级：P1）

同一会议中，远端同事用英文发言。用户**不需要切换耳机、不需要打开字幕、不需要做任何手动操作**，就能从自己的 Mac 默认扬声器/耳机里听到流式中文译音，与原英文音频几乎同步。

**为什么优先**：与用户故事 1 互为镜像，构成完整双向闭环。两条切片各自独立可交付（先上故事 1 或先上故事 2 都能交付价值），并行 P1。「让我听懂对方」是参会成败的另一半。

**独立测试**：在 Teams 测试通话中由对端播放标准商务英文台词；本系统从虚拟输出设备捕获 Teams 音频，执行下行管线；用户耳机端可听到流式中文译音，首段译音延迟可由外部时钟测得。

**验收场景**：

1. **假设** 下行同传已开启、Teams 输出已路由到虚拟捕获设备，**当** 远端讲话开始，**那么** 用户耳机端在远端开口后 ≤ 1200 ms 内开始听到对应中文译音（2026-05-07 宪章修订自 800 ms；持续优化软目标 ≤ 1000 ms）。
2. **假设** Teams 会议中存在多段英文发言之间的自然间隔，**当** 间隔 < 1 秒时，**那么** 系统将其视为同一段语流不强制截断；**当** 间隔 ≥ 5 秒时，**那么** 系统闭合上一段、并准备好接收下一段。
3. **假设** 下行音频与上行音频同时存在，**当** 双向同传同时运行，**那么** 两条管线互不串扰：用户听到的中文译音不混入用户自己合成的英文译音；远端听到的英文译音不混入用户的中文原音。

### 用户故事 3 — 实时状态面板：用户随时看见「自己说了什么、对方说了什么、延迟多少」（优先级：P2）

用户在会议进行时，可以快速瞄一眼一个**轻量本地界面**（不要求是原生 App），获取以下信息：当前会话已运行时长；最近一段中文识别原文与英文译文；最近一段英文识别原文与中文译文；当前首段译音延迟与端到端延迟（滚动 p50/p95）；外部服务连接状态。

**为什么优先**：同传系统对用户最大的不安来自「不知道自己被翻译成了什么」。本故事不阻塞用户故事 1/2 的可用性，但项目宪章原则 III 明确要求「用户必须随时能观察到延迟、识别文本与译文」，因此必须实现。可在故事 1/2 上线之后第二批交付。

**独立测试**：在双向同传运行中，打开本地状态界面（CLI 或本地 Web 页面均可）；任意时刻看到的最新一段识别/译文与该时刻系统行为对齐；任意时刻面板显示的延迟数字与外部探针测得的延迟差异 ≤ 200 ms。

**验收场景**：

1. **假设** 同传已运行，**当** 用户打开状态面板，**那么** 面板中「识别文本」区在 ≤ 1 秒内显示出当前正在被识别的中文片段（部分识别 partial 与最终识别 final 必须视觉可区分）。
2. **假设** 状态面板已打开，**当** 一段译文被合成并播出，**那么** 该段译文文本在 ≤ 1 秒内出现在面板「译文」区。
3. **假设** 任一外部服务（STT / 翻译 / TTS）连接异常，**当** 异常发生，**那么** 面板对应服务的连接状态在 ≤ 5 秒内变为非「健康」，并附带「发生了什么 + 用户下一步可以做什么」的两段式提示。

### 用户故事 4 — 启停、暂停与故障自愈：把同传当成开关而不是调试任务（优先级：P3）

用户应能用单次操作启动整个双向同传会话；在会议中临时切换不同输入设备（如外接耳机麦克风）或临时静音不应导致系统崩溃或丢失会话上下文；网络瞬断（≤ 30 秒）应自动重连并对用户显式告知「已恢复」。

**为什么优先**：提升体验与稳定性，但功能上故事 1–3 已经覆盖了核心价值。在 P1/P2 稳定后再做韧性强化更经济。

**独立测试**：在会话进行中模拟网络断开 5 / 15 / 30 秒；模拟切换 Mac 输入设备；模拟点击「暂停」再「继续」。每种动作后系统应在 ≤ 30 秒内恢复正常工作，状态面板与音频侧均无残留垃圾片段。

**验收场景**：

1. **假设** 同传运行中，**当** 用户从 Mac 系统设置切换默认输入设备到另一支麦克风，**那么** 系统不丢失当前会话、不崩溃，最多在 5 秒内自动接管新设备并继续工作。
2. **假设** 同传运行中，**当** 用户点击「暂停」，**那么** 系统停止向 Teams 写入英文音频、停止向用户播放中文音频；点击「继续」后 ≤ 2 秒内恢复双向流。
3. **假设** 网络瞬断 ≤ 30 秒，**当** 网络恢复，**那么** 系统自动重连各外部服务，并在状态面板显式提示「已恢复」；期间产生的不可恢复音频片段被清晰标记或丢弃，不污染上下文。
4. **假设** 同传运行中，**当** Whisper.cpp 子进程因 OOM 或意外信号退出，**那么** CLI 主进程在 ≤ 5 秒内自动 respawn 该子进程，状态面板显式提示「Whisper.cpp 已崩溃并自动恢复」；会话上下文（最近 final 对照、SessionId、术语表注入状态）**不**丢失；同一子进程 60 秒内崩溃 ≥ 3 次时系统转入降级状态并显式告知用户。

### 边界与异常情况

- **中英混讲（用户中文里夹英文专有名词）**：上行链路必须保留英文原词，不得反复二次翻译。
- **远端非英文发言（混入第三语言、口音重的英文、强背景噪声）**：下行链路在置信度低于阈值时应优先保静默，而非「幻听」出错误中文。
- **数字、金额、日期、人名**：翻译过程中不得改写为意译；保留原始数字与称谓。
- **Teams 自身的系统提示音**（如有人加入会议）：下行捕获应将系统音效与人声区分，不应将提示音翻译为中文播报。
- **用户端使用蓝牙耳机**：切换音频路径不得让虚拟设备失效；蓝牙抖动期间允许短暂卡顿，但不得静默卡死。
- **回声/反馈环路**：下行合成的中文音频不得被上行麦克风再次拾取并送回云端识别（必须在音频路由层规避）。
- **API 配额耗尽 / 凭证失效**：必须给出可操作的明确提示（「密钥过期，请在 ~/xxx 中更新」），而非沉默失败。
- **长会话（≥ 2 小时）**：内存与延迟不应随时间显著恶化（对齐宪章原则 IV：24 小时增长 ≤ 5%）。
- **Teams 会议侧开启降噪 / AI 增强**：本系统对其的容忍策略需可配置；默认保持 Teams 默认设置不动。
- **首次安装未授权麦克风权限**：必须主动检测并引导用户去系统隐私设置中授予权限。
- **虚拟音频驱动未安装或被系统拒绝**：必须在启动前自检并阻止开始同传，给出可点击的安装/恢复指引。

## 需求 *（必需）*

### 功能需求

#### A. 音频采集与路由

- **FR-001**：系统**必须**从 Mac 默认输入设备实时捕获用户中文语音流，采样率默认 16 kHz / 单声道，可通过配置覆盖。
- **FR-002**：系统**必须**将上行链路合成的英文音频写入一个虚拟音频输入设备（**v1 路由方案**：使用 **BlackHole 2ch** 开源免费虚拟音频驱动，通过 `brew install blackhole-2ch` 安装；本系统以 CoreAudio 客户端身份将合成英文音频流式写入 BlackHole 2ch 设备；用户在 Teams 应用设置中把麦克风输入源切换为 BlackHole 2ch，即完成上行路由）；写入**必须**以流式方式进行，**不得**等待整段音频生成后再一次性写入。
- **FR-003**：系统**必须**从虚拟音频输出设备实时捕获 Teams 桌面端的英文输出音频流，作为下行链路输入（**v1 路由方案**：用户在 macOS「音频 MIDI 设置」中创建一个 Aggregate Device，成员包含 BlackHole 2ch 与用户的物理耳机；用户在 Teams 应用设置中把扬声器输出源切换为该 Aggregate Device，Teams 音频会**同时**送至 BlackHole 2ch（供本系统下行 STT 捕获）与用户耳机（供用户直接听到 Teams 原英文）；本系统下行合成的中文译音独立通过 **Mac 默认输出设备**（用户耳机/扬声器）播放，与 Teams 原英文在用户耳机端混合播放）。
- **FR-004**：系统**必须**将下行链路合成的中文音频通过 Mac 默认输出设备（用户的耳机/扬声器）实时播放。
- **FR-005**：系统**不得**要求用户安装额外物理硬件，也**不得**修改 Mac 标准音频驱动；唯一允许的内核扩展是用户自行安装的虚拟音频设备（BlackHole / Loopback / 同类）。
- **FR-006**：系统**必须**提供一份首次运行向导（脚本或 Web 页面形式），引导用户完成以下步骤并对每一步做自动检测验证：(a) 通过 Homebrew 安装 BlackHole 2ch（`brew install blackhole-2ch`）并按提示重启 macOS 一次以注册驱动 → 自检 BlackHole 2ch 是否已注册为 CoreAudio 设备；(b) 在「音频 MIDI 设置」中创建一个 Aggregate Device 并将其成员设为 BlackHole 2ch + 用户耳机 → 自检 Aggregate Device 是否存在且成员匹配；(c) 在 Teams 设置中将麦克风输入源切换为 BlackHole 2ch、扬声器输出源切换为该 Aggregate Device → 通过短促测试音验证两个方向均通；(d) 在 macOS 系统隐私设置中授予本系统麦克风权限 → 自检授权状态；(e) 填入 DeepSeek API Key 到环境变量 `DEEPSEEK_API_KEY` 或本地配置文件 `~/.config/teams-voice-interpreter/config.toml` → 自检凭证可用（一次轻量 ping 调用）。任一步失败时**必须**给出包含「发生了什么 + 用户下一步如何做」的两段式提示。

#### B. 流式翻译管线（上行与下行）

- **FR-007**：上行链路**必须**采用流式 STT 接口（**v1 服务栈**：本地 **Whisper.cpp Streaming** 分支；默认模型 `whisper-small`，可配置升级到 `medium` / `large-v3`；优先启用 Apple Silicon Metal / Core ML 加速）持续输出 partial 与 final 识别片段；**不得**等待整句结束后才提交识别结果。
- **FR-008**：上行链路**必须**在每次收到可用 partial / final 片段时立即触发增量中→英翻译（**v1 服务栈**：DeepSeek API 的 streaming chat completion，模型默认 `deepseek-chat`，启用 SSE 流式以最小化首 token 延迟）；**不得**在 STT final 之前阻塞翻译队列。
- **FR-009**：上行链路**必须**采用流式 TTS 接口（**v1 服务栈**：**Edge-TTS** 通过 `edge-tts` Python 客户端调用 Microsoft Edge 浏览器免费语音合成接口；默认英文音色 `en-US-AriaNeural`，支持配置切换），使首段英文音频在用户开口后被远端听到的延迟 ≤ 1200 ms（硬阈值，2026-05-07 宪章修订自 800 ms；持续优化软目标 ≤ 1000 ms，与 SC-001 一致）；**不得**整段合成后再一次性写入虚拟麦克风。
- **FR-010**：下行链路**必须**以与 FR-007 / FR-008 / FR-009 等同的流式策略实施英→中识别（同款 Whisper.cpp Streaming，模型可独立配置）、翻译（同款 DeepSeek API，反向语言对，独立流式连接）与合成（**v1 服务栈**：**Edge-TTS** 中文音色，默认 `zh-CN-XiaoxiaoNeural`，支持配置切换）。
- **FR-011**：翻译模块**必须**保留专有名词、英文缩写、数字、日期、金额的原始或常见映射，不得自由改写。
- **FR-012**：翻译模块**必须**接收两层上下文以提升一致性：(a) **会话滚动上下文**——最近 N 句已 final 的双语对照，N 默认 8 句、可配置；(b) **静态术语表**——用户在 `~/.config/teams-voice-interpreter/glossary.toml` 中维护的中英对照术语表，每条至少含 `zh` / `en` 两字段、可选 `note` 字段（向 LLM 解释保留原写法的理由），v1 上限 200 条。会话启动时系统**必须**一次性把术语表合成进 DeepSeek 翻译调用的 system prompt；**v1 不支持**会话运行中术语表热更新（自适应学习延至 v2）。文件不存在或为空时**必须** graceful 处理为「无自定义术语」，**不得**因此阻止会话启动。**术语表延迟预算**：0 条术语与 200 条术语两档都必须纳入 BM-5，200 条档对 `MT_FIRST_TOKEN` 的 p95 增量应 ≤ 200 ms；若超过该增量，必须在启动时裁剪为 top-K 术语或提示用户拆分术语表。
- **FR-013**：当 STT 在 ≥ 5 秒窗口内未检出语音活动（VAD）时，系统**必须**闭合上一段翻译片段、释放 partial 缓冲，并停止向 TTS 推送空白。**partial → final 升级延迟预算**：从 VAD 第 167 帧（≈ 5 秒）触发 close_segment 到 `TranscriptSegment.kind=FINAL` 写入内存的耗时 ≤ 200 ms（不含等待 5 秒静音本身）；该 200 ms 包含 Whisper.cpp 子进程 finalize 推理 + JSON Lines 解析 + 主进程消息总线分发。**连续长语音缓冲上限**：若单人连续发言 ≥ 30 秒仍未触发 VAD 静音闭合，系统必须每 30 秒滚动封口一个可继续拼接的 final 段，并保留最近 10 秒音频作为下一段上下文；单个 partial 缓冲不得超过 30 秒或 1,000 token，避免 5 分钟无停顿发言导致内存或延迟窗口外溢。

#### C. 会话生命周期与可观测性

- **FR-014**：系统**必须**暴露两个用户表面（**v1 决定**：仅 CLI + 本地 Web 控制台，**不**追加 macOS 状态栏菜单、终端 TUI 或 macOS 系统通知）：(a) **CLI 子命令** `start` / `pause` / `resume` / `stop` / `status`，用户可在终端中执行启停操作；(b) **本地 Web 控制台**，CLI 启动同时拉起后端进程并绑定到 `http://localhost:<port>`（默认端口 `8765`，可配置），用户在浏览器中执行启停与查看状态；用户**必须**能从任一表面完成：开始 / 暂停 / 继续 / 停止双向同传会话。
- **FR-015**：用户表面**必须**在用户触发「开始」操作后 ≤ 1 秒内显示「已收到 / 处理中」状态（对齐宪章原则 III）。
- **FR-016**：用户表面**必须**实时显示：(a) 当前会话已运行时长；(b) 最近一段中文识别原文与英文译文；(c) 最近一段英文识别原文与中文译文；(d) 首段译音延迟与端到端延迟的滚动 p50 / p95；(e) STT、翻译、TTS 三类外部服务的连接状态。
- **FR-017**：系统**必须**不丢失任何一次会话内已 final 的识别与翻译片段，即使在用户切换设备、暂停 / 继续，或 ≤ 30 秒网络瞬断之后。

#### D. 容错与降级

- **FR-018**：任一外部 API（STT / 翻译 / TTS）瞬时失败时，系统**必须**自动按指数退避重连，并在状态面板上显示状态变化；**不得**直接终止整个会话。瞬断期间该方向不得继续生成新的假译音；可继续播放的旧译音最大滞后 ≤ 2 秒，超过后必须静音并标记该方向为「正在重试」。网络恢复后，若 30 秒窗口内可恢复，系统必须继续同一 SessionId；若无法恢复，则按 FR-019 降级。
- **FR-019**：若 STT 连续 ≥ 30 秒无法恢复，系统**必须**停止该方向的音频外发并显式提示用户；**不得**向 Teams / 扬声器持续输出静音或假数据。
- **FR-020**：用户麦克风权限被撤销或虚拟音频设备消失时，系统**必须**立即停止该方向，并向用户给出包含「发生了什么 + 下一步如何做」的两段式提示。

#### E. 配置、分发与隐私

- **FR-021**：系统**必须**以脚本（Python / Go）或 Web 应用形式分发；**不得**以原生 macOS App Bundle、Teams 插件 / Add-in、Office 365 Add-in 等形式存在。
- **FR-022**：系统**必须**通过环境变量或本地配置文件接收外部服务凭证（DeepSeek API Key 及任何 STT / TTS 凭证）；**不得**在源码或仓库中硬编码任何密钥。
- **FR-023**：系统**默认不得**在本地或远端持久化原始音频；如启用诊断日志，**必须**在用户表面显式告知并提供单开关关闭。
- **FR-024**：系统**必须**在当前会话进行期间于内存中**完整保留**双向识别原文与译文（用于 FR-027 导出），**不得**因滚动窗口截断而丢弃；状态面板的「最近识别 / 最近译文」**默认仅显示**最近 100 条以控制 DOM 渲染负担，但底层内存中完整记录**必须**直到会话停止后才释放。会话停止时若用户未触发 FR-027 导出，所有内存中的识别 / 译文文本**必须**立即释放。**不得**默认在磁盘或远端持久化任何会话内容；持久化只能由用户在 Web 控制台显式触发 FR-027「导出」操作。
- **FR-025**：系统**不得**依赖任何「整段录制 → 后处理 → 整段合成」的事后翻译模式；任何片段从被识别到被合成的全路径**必须**是流式的。
- **FR-026**：系统在 v1 阶段**必须**采用单实例约束：同一时刻只允许存在一个活跃的同传会话（一个 SessionId、一个 Whisper.cpp 推理进程、一个 Web 控制台监听端口、一个 BlackHole 2ch 写入连接）。当用户尝试在已有活跃会话时再次执行 CLI `start` 或 Web 控制台「开始」操作，系统**必须**拒绝并返回包含「发生了什么 + 用户下一步如何做」的两段式提示（例：「检测到已有活跃会话 SessionId=<id>，请先在原终端 / 浏览器执行 stop 操作，再启动新会话」）。**不得**自动 kill 已有会话或在用户不知情时强占资源。
- **FR-027**：用户**必须**能在 Web 控制台点击「导出」按钮，将当前会话的完整双语对照下载为一份 Markdown 文件（默认文件名 `teams-session-<开始时间戳>.md`）。文件结构**必须**包含：(a) 会话头部元数据——开始时间、停止时间（若已停止）、上行 / 下行启用标志、所用服务栈版本快照；(b) 按时间顺序的双语对照条目，每条含 `timestamp`、`direction`（上行 = 用户中文 → 远端英文 / 下行 = 远端英文 → 用户中文）、`zh`、`en` 四字段；(c) **不得**包含延迟元数据、识别置信度、服务调用 trace、原始音频字节（诊断模式导出延至 v2）。导出操作**不得**中断或暂停当前活跃会话；会话停止后用户**仍可**在 Web 控制台触发一次"快照导出"（仅在 FR-024 内存释放前的窗口期内有效），过期后导出按钮**必须**置灰并提示「会话已结束、内存已释放」。
- **FR-028**：CLI 主进程**必须**作为进程内 supervisor 监控核心子进程（包括但不限于 Whisper.cpp 推理子进程、Edge-TTS 流式合成子进程、虚拟音频写入子进程）。任一子进程异常退出时，主进程**必须**在 ≤ 5 秒内自动 respawn 该子进程，并在 Web 控制台状态面板与日志中显式提示「子进程 `<name>` 已崩溃并自动恢复」；respawn **不得**清空滚动窗口、**不得**重置 SessionId、**不得**丢失术语表注入状态。当同一子进程在 60 秒滚动窗口内崩溃 ≥ 3 次时，主进程**必须**停止该方向的同传并向用户给出「两段式」提示，避免无限崩溃循环。**不得**引入 launchd / supervisord / pm2 等系统级守护进程（与 FR-014 v1 用户表面「不产生 launchd plist」一致）。
- **FR-029**：当 CLI 主进程或任一关键子进程崩溃时，系统**必须**通过 Python 信号处理器或 `atexit` 钩子写一份匿名崩溃报告到 `~/.cache/teams-voice-interpreter/crash-<unix-timestamp>.log`。报告**必须**包含：(a) Python 与关键依赖（whisper.cpp / edge-tts / fastapi / httpx）版本；(b) 崩溃时刻的 stack trace；(c) 各外部服务（DeepSeek / Whisper / Edge-TTS）最近一次连接状态快照；(d) 系统资源快照（RAM / CPU 使用）。报告**不得**包含：(a) 任何识别原文或译文文本；(b) 任何原始音频字节；(c) 服务凭证或 API Key；(d) 用户家目录路径或个人信息（路径需脱敏为 `~`）。崩溃报告**必须**有数量上限（默认保留最近 20 份，按时间戳轮转删除），避免长期占用磁盘。

### 关键实体

- **会话（Session）**：一次「开始 → 停止」之间的同传上下文。属性：起止时间戳、上行 / 下行启用标志、累计延迟统计、所引用的服务凭证标识、状态面板渲染用的滚动片段窗口（最近 100 条）、**会话内完整双语对照记录**（按时间顺序、双向交错，用于 FR-027 导出，会话停止后未导出则立即释放）。
- **音频流（AudioStream）**：区分上行（用户输入 → Teams）与下行（Teams 输出 → 用户）。属性：方向、源设备 / 目的设备、采样率、声道数、活跃状态、累计字节数。
- **识别片段（TranscriptSegment）**：属性：所属方向、起止时间戳、partial / final 标志、原文文本、置信度、产生该片段的服务标识。
- **翻译片段（TranslationSegment）**：属性：源识别片段引用、目标语言文本、翻译模型 / 服务标识、首 token 延迟、整段完成延迟。
- **合成音频片段（SynthesizedAudioSegment）**：属性：所属翻译片段引用、采样率、字节流引用（流式块队列）、首字节出口时间、目标设备（虚拟麦克风 / 默认扬声器）。
- **延迟指标快照（LatencySnapshot）**：属性：滚动窗口、各阶段（采集 / STT / MT / TTS / 路由）耗时、首段译音延迟、端到端延迟、p50 / p95 / 平均 / 最大。
- **服务凭证（ServiceCredential）**：属性：服务类别（STT / MT / TTS）、提供商标识、密钥引用（不入库）、endpoint、配额阈值告警。
- **术语表条目（GlossaryEntry）**：用户配置的专有名词中英映射。属性：中文写法 `zh`、英文写法 `en`、可选备注 `note`（向 LLM 解释为何保留原写法）、来源（用户配置 / 未来 v2 系统内置）。会话启动时所有条目合成为 DeepSeek 翻译调用 system prompt 的一部分；运行时只读、**不**热更新。

## 成功标准 *（必需）*

### 可度量结果

- **SC-001**：上行链路**端到端首段译音延迟**的中位时延 **≤ 1200 ms（硬阈值，发布门禁）/ ≤ 1000 ms（软目标，持续优化）**；p95 **≤ 2000 ms（硬阈值）**。**> 1500 ms 视为二次修订触发阈值**，启动 (a) 服务栈替换 / (b) 模型降档 / (c) 二次宪章修订三选一处置。**修订依据（2026-05-07）**：BM-4 实测 DeepSeek MT first token p50 566-598 ms 与 C+α 测得整段 ASR ≤ 310 ms 累加，端到端首段译音延迟物理下限在当前服务栈下 ≈ 1100-1170 ms（详见 perf-report.md「DeepSeek MT first token 真实化（BM-4）」段）；原中位 ≤ 800 ms / p95 ≤ 1.5 s 阈值已通过 2026-05-07 宪章修订 PR 调整。**测量定义**：起点 = 用户麦克风 `sounddevice.InputStream` callback 接收到首个非静音帧的时间戳；终点 = 本系统 `BlackHoleWriter` 写入虚拟麦克风的首个非静音字节的时间戳（远端 Teams 实际听到时刻 = 本时刻 + 不可观测的 Teams 网络上行延迟，**不**纳入 SC-001 度量）。**预算分解**：capture + STT + MT_FIRST_TOKEN + TTS_FIRST_BYTE + AUDIO_ROUTE 五阶段串联；其中 MT_FIRST_TOKEN 受宪章原则 IV「LLM 翻译首 token ≤ 800 ms」独立约束（**子预算**而非端到端预算）；本 SC-001 是端到端总和的可观测代理。**软目标语义**：≤ 1000 ms 不构成发布门禁，但 release notes / perf-report 必须公布当前 p50 与软目标距离，避免"修订即放弃"。**实测超过 1200 ms 硬阈值时**发布必须阻断，直到完成服务栈替换 / 模型降档 / 通过独立宪章修订 PR 进一步调整预算。
- **SC-002**：下行链路**端到端首段译音延迟**中位 **≤ 1200 ms（硬阈值）/ ≤ 1000 ms（软目标）**；p95 **≤ 2000 ms（硬阈值）**（数值阈值同 SC-001，2026-05-07 宪章修订 PR 自原 800 ms / 1.5 s 一并调整）。> 1500 ms 视为二次修订触发阈值，处理方式同 SC-001。**测量定义**：远端用户的开口时刻**不可观测**（用户端无法访问远端 PC 时钟），以**远端音频经 Teams 通道首字节进入本系统 BlackHole 2ch 输入流**的时间戳作为起点代理；终点 = 本系统 `DefaultOutputWriter` 写入用户耳机/扬声器的首个非静音字节时间戳。本 SC 度量的是「Teams 输出 → 用户耳机」段，**不**含 Teams 应用本身的网络下行延迟。
- **SC-003**：端到端「整句完成」延迟 p50 ≤ 2.5 s、p95 ≤ 4.0 s（对齐宪章原则 IV）。**测量定义**：起点 = 用户/远端结束发音后 ≥ 600 ms 静音被 VAD 升级为 final 的瞬间（即 `TranscriptSegment.kind=FINAL` 写入时间戳）；终点 = 该 final 段对应的 `SynthesizedAudioSegment` 最后一个 audio chunk 写入目标设备的时间戳。本 SC 与 SC-001（首段播出）正交，覆盖整段译音从输入闭合到输出闭合的全程。
- **SC-004**：在标准 Apple Silicon Mac（M2 及以上）、稳定 ≥ 50 Mbps 网络下，**连续 60 分钟双向同传**：用户感知中断次数 = 0（**用户感知中断**定义：用户耳机端连续 ≥ 3 秒无任何译音输出 / Web 控制台 `services_health` 出现 ≥ 1 次「unavailable」状态；子进程 supervisor 内部 respawn 在 ≤ 5 秒恢复且不影响输出，**不**计为中断）。**24 小时持续运行内存增长 ≤ 5%**（**基线测量点** = 启动后 5 分钟稳态时刻的 RSS；**适用工况** = 持续对话工况，每分钟 ≥ 30 秒有效语音输入；持续静音工况另由 SC-004b 隔离覆盖：连续 24 小时静音工况下内存增长 ≤ 2%）。**中间检查点**：1 小时增长 ≤ 1%、6 小时增长 ≤ 2%、12 小时增长 ≤ 3.5%；任一中间检查点超阈值必须提前判为内存泄漏风险，不得等到 24 小时结束后才处置。
- **SC-005**：普通话母语者在标准商务对话场景下，对译文进行盲测可懂度评分（5 分制）≥ 4/5。**盲测协议**：评估者 ≥ 5 名（母语为目标语言、有 ≥ 1 年商务会议经验）；样本 ≥ 30 对句子（覆盖 IT / 法务 / 财务 / 销售四类场景各 ≥ 7 句）；评估者**不**知晓哪条译文出自本系统、哪条出自人类参考；采用 1–5 Likert 量表；统计达标条件 = 平均分 ≥ 4.0 且 95% 置信区间下界 ≥ 3.7（n=150 样本评分点：5 评估者 × 30 句）。**专有名词 / 数字 / 日期保留正确率 ≥ 95%**：**保留**定义 = 目标语言译文中保留原始书写形式（含大小写、连字符）或采用术语表（GlossaryEntry）的目标映射；样本 = 评估者标注的 30 句中所有专有名词 / 数字 / 日期出现位置。
- **SC-006**：任一外部服务出现瞬时不可用时，用户在 ≤ 5 秒内能在状态面板上看到带「下一步建议」的两段式错误提示。**测量定义**：起点 = 第 1 次 API 调用失败 / 网络断开被客户端检测到的瞬间（**非**退避策略退出最后一次重试的瞬间——FR-018 退避序列 250+500+1000+2000+4000 = 7.75 s 的累计耗时与本 SC 度量解耦）；终点 = WebSocket 推送 `service_error` 事件且前端 Toast 区 DOM 显示完成的时刻。退避策略本身在后台执行的同时，状态面板**必须**先行推送「正在重试 第 N 次」可视提示。会话不中断（除非该方向的服务连续 ≥ 30 秒不可恢复，触发 FR-019）。
- **SC-007**：从全新 Mac 用户首次执行 `git clone` / `pip install` 命令到首次成功听到一段译音 ≤ 15 分钟。**全新基线定义**：(a) macOS 13+ 已安装；(b) Homebrew 已安装且可用；(c) Python 3.11+ 已安装（`python3 --version` 可执行）；(d) 用户已注册并持有 DeepSeek API Key；(e) 网络条件 ≥ 50 Mbps；(f) 用户耳机已连接。**纳入计时**的步骤：`brew install blackhole-2ch`（约 30 秒）+ macOS 重启（约 60–90 秒）+ Whisper 模型 ≈ 470 MB 下载（约 2–4 分钟）+ Aggregate Device 创建（约 1 分钟引导）+ Teams 路由切换（约 1 分钟）+ wizard 自检（约 2 分钟）+ 首次合成 / 译音验证（约 30 秒）。**不**纳入：(a)（b）（c）的预装时间；macOS 重启所需的硬件唤醒时长。
- **SC-008**：状态面板从识别 / 翻译事件发生到面板显示新内容的滞后 ≤ 1 秒（对齐宪章原则 III「1 秒内反馈」）。**测量定义**：起点 = 内部消息总线（asyncio Queue）中 `transcript_partial` / `transcript_final` / `translation_first_token` 事件被产生的时间戳（即子进程 stdout JSON 行被主进程消费的瞬间）；终点 = 浏览器 DOM 中对应文本节点的 `MutationObserver` 触发时刻（前端通过 WebSocket 接收 + `htmx` swap + 浏览器 paint 完成）。该滞后包含：消息总线分发 + WebSocket 推送 + 网络往返（localhost ≈ 0.5 ms）+ 前端 DOM 更新。
- **SC-009**：系统分发产物中：原生 macOS App Bundle（`.app`）数量 = 0、Teams 插件 / Office Add-in 数量 = 0、本项目分发的内核扩展数量 = 0（用户自行 `brew install` 的第三方虚拟音频驱动如 BlackHole 2ch **不**计入本计数）。**注**：本条目本质是**分发与产物形式合规**约束（与宪章「不开发原生 Mac App」用户硬约束直接对应），**非**性能维度；保留在「成功标准」段是因为它是 v1 不可妥协的可度量验收条件，与性能 SC 共用同一审计流程；新增产物分类时优先迁移至独立的 Distribution / Compliance 段。
- **SC-010**：在标准 Apple Silicon Mac（M2 及以上）上的稳态运行平均 CPU 占用 ≤ 30%；稳态 RAM ≤ 500 MB。≤ 40% CPU 与 ≤ 1.6 GB RAM 仅作为 plan §复杂度追踪行 1 / 2 登记的风险观测阈值 / 修订触发阈值，不构成发布放行标准或发布豁免。**稳态定义**：启动后 ≥ 5 分钟、双向同传持续运行、每分钟 ≥ 30 秒有效语音输入；测量窗口 = 5 分钟滚动平均；硬件基线 = M2 Pro 16 GB（Intel x86_64 单独度量，不在本 SC 范围）。本预算的适用负载**必须**包含：上行 + 下行两个 Whisper 子进程、两个 Edge-TTS 流式合成通道、DeepSeek 双向流式连接、本地 FastAPI、WebSocket ≥ 5 Hz 推送、Web 控制台 DOM 更新、会话内完整双语对照最多 20,000 个 final 条目。**已知风险**：Whisper.cpp small q5_0 单实例 1.0–1.5 GB RAM + 25–40% CPU；**实测超过宪章预算时**发布必须阻断，直到完成模型降档 / 服务栈替换，或通过独立宪章修订 PR 正式调整预算。
- **SC-011**：分发产物（README、首次运行向导、Web 控制台首屏）**必须**包含一份显著位置的「监管严格场景免责声明」，明确列出医疗 / 律师 / 政府 / 金融 / HR 等不适用场景；首次运行向导**必须**以勾选确认 + 时间戳记录方式要求用户阅读，未确认时**必须**阻止启动同传会话。
- **SC-012**：已安装用户的冷启动延迟 p95 ≤ 10 秒。**测量定义**：起点 = 用户执行 CLI `start` 或 Web 控制台 `POST /api/control/start` 被接收；终点 = 设备自检、单实例锁、WebSocket 状态流、Whisper 模型 mmap / 子进程 heartbeat、Edge-TTS voice ping、DeepSeek ping 均就绪并在面板显示「可开始说话」。本 SC **不**包含首次安装、Homebrew 安装、macOS 重启、Whisper 模型首次下载；首次安装仍由 SC-007 约束。
- **SC-013**：操作恢复延迟必须可度量：暂停 → 继续后，上行与下行音频恢复输出 p95 ≤ 2 秒；运行中切换输入设备后，新设备接管 p95 ≤ 5 秒；≤ 30 秒网络瞬断恢复后，同一 SessionId 的状态面板显示「已恢复」p95 ≤ 5 秒，且故障期间旧译音滞后不得超过 FR-018 的 2 秒上限。

## 假设

- **目标用户**：中文母语、参加英语 Teams 商务会议的 Mac 用户；具备配置环境变量与执行命令行脚本的基础能力；能上网访问 DeepSeek 等外部 API。
- **硬件环境**：Apple Silicon 或较新 Intel Mac；内置麦克风与默认扬声器/耳机已可用；用户接受安装一款主流虚拟音频设备（BlackHole 或 Loopback 或同类）。
- **会话规模**：v1 聚焦 1:N 商务会议场景，单方向同时只有一位发言人；多人同时发言、说话人分离不在 v1 范围。
- **语言对**：v1 仅支持中→英（上行）与英→中（下行）；其他语言对在后续版本规划。
- **延迟语义对齐**（重要，2026-05-07 宪章修订后）：SC-001 / SC-002「首段译音延迟」（time-to-first-translated-audio）现采用 **≤ 1200 ms 硬阈值 + ≤ 1000 ms 软目标 / p95 ≤ 2000 ms 硬阈值**，覆盖 capture + STT + MT_FIRST_TOKEN + TTS_FIRST_BYTE + AUDIO_ROUTE 五段串联。宪章原则 IV 同时对 LLM 单段 first token 给出 ≤ 800 ms 子约束（属于 MT_FIRST_TOKEN 阶段），与端到端阈值并行。**修订背景**：原 SC-001 中位 ≤ 800 ms 与宪章 IV LLM 800 ms 在工程上不可同时无损达成 —— BM-4 实测 DeepSeek MT first token p50 566-598 ms 加 ASR / TTS / AUDIO_ROUTE 累加超 1100 ms（详见 perf-report.md「DeepSeek MT first token 真实化（BM-4）」段）；2026-05-07 宪章修订 PR 把 SC-001 / SC-002 端到端阈值调整为 1200 ms（硬）/ 1000 ms（软）以对齐工程现实。整段端到端「整句完成」延迟仍由 SC-003（p50 ≤ 2.5 s / p95 ≤ 4.0 s）独立约束，本次未修订。
- **流式管线必备**：任何「整句录制 → 后处理 → 整段合成」的事后翻译实现**不**满足本规约；流式 STT、流式翻译、流式 TTS 三者必须同时具备。
- **运行表面**：默认运行表面为本地后台进程 + 浏览器访问 `http://localhost:<port>` 的状态/控制页；同时提供 CLI 子命令用于启停。允许在后续迭代中追加状态栏菜单等轻量表面，但仍**不**构建原生 macOS App。
- **隐私边界**：用户接受将原始音频与识别文本经加密通道发送至所选外部服务（DeepSeek 等）；不接受时该用户场景不在 v1 范围。
- **网络可用性**：假定在线场景下网络抖动 ≤ 30 秒；离线 / 长断网下的本地化模式不在 v1 范围。
- **v1 适用场景边界（合规免责）**：v1 **不**适用于以下监管严格场景：医疗咨询 / 诊疗、律师-客户特权对话、政府或机要事务、金融合规通话、HR 与员工敏感事务，以及任何对录音 / 转写 / 翻译有特殊法律义务的场景。v1 仅面向**普通商务交流场景**的**个人用户自用**。用户**必须**自行确保所在司法管辖区（包括但不限于欧盟 GDPR、中国《个人信息保护法》、美国各州录音同意法、加州 CIPA 等）下的合规性，包括但不限于事先告知远端会议方"本端正在使用语音转写与机器翻译"。任何监管严格场景或团队 / 企业级部署**延至 v2**，并将作为独立 feature 重新规约。
- **v1 单实例约束**：v1 仅支持**单会话单 Teams**。同一 Mac 上**不**支持多个并行的同传会话（即不支持同时为两个 Teams 会议做同传）；尝试启动第二个会话时系统**必须**拒绝并提示用户先停止当前会话。该约束的工程动机：(1) Whisper.cpp small 单实例已占用 1.0–1.5 GB RAM，并行实例直接突破宪章 IV「稳态 RAM ≤ 500 MB」预算；(2) 与「个人自用 + 轻量级」路线一致；(3) 多账号 / 多会议并行场景属于团队部署，延至 v2。
- **v1 崩溃恢复策略**：CLI 主进程作为进程内 supervisor 监控核心子进程（Whisper.cpp / Edge-TTS / 虚拟音频写入），子进程崩溃自动 respawn（FR-028）；主进程本身崩溃由用户手动 restart，**不**引入 launchd / supervisord / pm2 等系统级守护，与 v1 用户表面「不产生 launchd plist」一致。崩溃前写匿名报告到 `~/.cache/teams-voice-interpreter/`（仅 stack trace + 服务状态，**不**含音频 / 对话 / 凭证），最近 20 份轮转保留；详见 FR-029。该策略与「默认不持久化」（FR-023）兼容——崩溃报告不属于「会话内容」。
- **回声规避**：假定用户使用耳机；外放扬声器场景下回声抑制效果不在 v1 强保证范围（建议但不强制）。
- **v1 服务栈（已锁定）**：
  - **翻译 / LLM**：DeepSeek API（`deepseek-chat` 模型，启用 SSE streaming），按 token 计费。月度成本估算：每天 2 小时双向商务会议约 ¥0.3–1，**月度 < ¥10**。
  - **流式 STT**：本地 Whisper.cpp Streaming 分支（候选实现 `whisper-streaming` / `faster-whisper-streaming`），默认 `whisper-small`（约 466 MB）+ Apple Silicon Metal 后端，**零按量费用**。
  - **流式 TTS**：Edge-TTS（`edge-tts` Python 客户端调用 Microsoft Edge 浏览器免费语音合成接口），**零按量费用**。
  - **总月度运行成本**：仅 DeepSeek 翻译费用，**总计 < ¥10/月**，与「低成本、严控按量计费」用户初衷一致。
- **v1 音频路由方案（已锁定）**：
  - **虚拟音频驱动**：BlackHole 2ch（开源免费，GPL 协议；通过 `brew install blackhole-2ch` 安装，安装后需重启 macOS 一次以注册驱动）。
  - **上行路由**：本系统合成英文音频 → 写入 BlackHole 2ch（作为输出设备） → Teams 麦克风源选 BlackHole 2ch → 远端听到。
  - **下行路由**：Teams 输出 → macOS 原生 Aggregate Device（成员 = BlackHole 2ch + 用户耳机） → 同步分两路：(i) BlackHole 2ch 被本系统作为输入设备捕获，进入下行 STT 管线；(ii) 用户耳机直接听到 Teams 原英文。
  - **中文译音回放**：本系统合成中文音频通过 Mac **默认输出设备**（即用户耳机本身，独立于 Aggregate Device）播放，与 Teams 原英文在用户耳机端自然混合。
  - **金钱成本**：0 元（与 Q1 服务栈一致）。
  - **回声规避说明**：因下行 STT 输入源仅来自 BlackHole 2ch（Teams 应用音频），上行麦克风源仅来自 Mac 内置麦，两路在驱动层物理隔离，**不**会出现"自己合成的中文被自己拾取再次翻译"的回声环路；外放扬声器场景仍存在物理回声风险，此场景不在 v1 强保证范围（与既有「假设」回声规避条款一致）。
- **v1 用户表面（已锁定）**：
  - **CLI**：Python 入口（形如 `python -m teams_voice_interpreter <subcommand>` 或 `tvi <subcommand>`，最终命令名待 plan 阶段决定）暴露 `start` / `pause` / `resume` / `stop` / `status` 子命令。
  - **本地 Web 控制台**：CLI 启动同时拉起 FastAPI（推荐）或 Flask 后端，绑定 `http://localhost:8765`（端口可配置）；前端为单页 HTML + 轻量 JS（推荐 HTMX 或原生 fetch + WebSocket，**不**引入 React / Vue 等重型框架以保持「轻量级」初衷）；面板内容覆盖 FR-016 全部要求。
  - **错误感知**：「发生了什么 + 下一步如何做」的两段式提示渲染在 Web 控制台顶部 Toast 区；当页面被遮蔽时，仅通过浏览器标签标题 / favicon 徽标与页内状态变化补充提醒；v1 **不得**调用浏览器原生 `Notification` API、**不得**使用 macOS 系统通知中心、**不得**驻留状态栏，避免触发 FR-014 用户表面约束与 FR-021 / SC-009 的分发形态红线。
  - **打包与分发**：`pip install` 或 `git clone` + `python -m`；**不**产生 `.app` 包、**不**产生状态栏菜单 bar 项、**不**产生 launchd plist 服务。
- **服务栈风险与降级**：
  - **Edge-TTS 是非官方接口**：`edge-tts` 为社区维护的逆向调用，**不是** Microsoft Azure 官方付费 API；存在因鉴权变更或接口下线导致整线瘫痪的风险。`/speckit.plan` 阶段**必须**设计降级路径，候选：(a) 切换到 Coqui XTTS-v2 本地推理（开源、约 1.8 GB 模型）；(b) 在用户显式同意付费时回落到 ElevenLabs Flash 或 Azure Speech 流式 TTS。
  - **延迟达成性进展（2026-05-07 已对齐）**：原 spec 起草时预估「端到端首段译音延迟期望中位 800–1200 ms、p95 约 1500 ms」与 SC-001 原 ≤ 800 ms 阈值存在达成风险。BM-4 / C+α 真实化测量已确认该区间（ASR 297 ms + MT first token 566 ms + TTS ~200 ms + ROUTE ~50 ms ≈ 1113 ms，详见 perf-report.md「DeepSeek MT first token 真实化（BM-4）」段）；通过宪章修订 PR（2026-05-07）正式把 SC-001 / SC-002 中位阈值从 ≤ 800 ms 调整为 ≤ 1200 ms（硬阈值）+ ≤ 1000 ms（软目标），p95 从 ≤ 1500 ms 调整为 ≤ 2000 ms（硬阈值）。后续若实测超过 1200 ms 硬阈值或超过 1500 ms 二次修订触发阈值，**必须**阻断后续实现与发布，直到完成服务栈替换、模型降档，或通过独立宪章修订 PR 进一步调整预算；不得仅在 `plan.md → 复杂度追踪` 登记退出计划后继续推进，**不得**默默放宽。
  - **本地资源预算紧张**：Whisper.cpp small 持续运行约 1.0–1.5 GB RAM、单核 25–40%，与宪章 IV「稳态 RAM ≤ 500 MB、CPU ≤ 30%」预算冲突。`/speckit.plan` 阶段**必须**评估降级到 `whisper-tiny`（约 75 MB）或重新协商宪章预算。
- **延迟基线测试 gating**：`/speckit.tasks` 必须包含一组在 plan 通过后立即执行的 benchmark 任务，覆盖：(a) Whisper.cpp small/medium 在目标设备的流式 partial 延迟分布；(b) DeepSeek streaming 首 token 延迟分布；(c) Edge-TTS 首字节延迟分布；(d) 端到端首段与整段延迟。基线结果**必须**写入 `specs/001-teams-voice-interpreter/perf-report.md`，并据此决定是否触发宪章修订或服务栈替换。
